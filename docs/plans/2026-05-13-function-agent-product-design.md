# ArchCritic 第一个真实 Agent 产品文档：功能与流线 Agent

编写日期：2026-05-13  
适用阶段：真实单 Agent v1  
目标：把当前演示评图中的“功能与流线”分项，升级为一个可解释、可追溯、可稳定输出结构化结果的真实 Agent。

## 1. 一句话定位

功能与流线 Agent 是 ArchCritic 的第一个真实评图 Agent。  
它专门评价建筑方案的功能满足、功能分区、流线组织和平面设计丰富性，目标不是替代老师打分，而是像课程助教一样，把学生方案中“功能是否缺漏、分区是否合理、流线是否冲突、平面是否只是机械排房间”这类问题先筛出来，并给出可执行的修改建议。

## 2. 它是不是提示词工程

它包含提示词工程，但不只是提示词工程。

一个可用的 Agent 至少由 6 个部分组成：

| 部分 | 作用 |
| --- | --- |
| 角色定义 | 告诉模型它扮演建筑设计课助教，不是泛泛聊天助手 |
| 输入整理 | 把项目、阶段、设计说明、图纸类型、Wiki 依据整理成模型能理解的上下文 |
| 知识检索 | 从 `wiki-test/wiki/评价维度/方案阶段/功能与流线` 读取规范、案例和评价维度 |
| 评价规则 | 明确看什么、怎么打分、什么情况下扣分 |
| 输出格式 | 强制返回固定 JSON，方便前端展示和数据库保存 |
| 质量校验 | 检查模型有没有乱写、漏字段、没有依据、分数越界等问题 |

所以第一版真实 Agent 应该按“提示词 + 知识库 + 输出约束 + 后端校验”的方式构建。

## 3. 产品目标

### 3.1 面向学生

学生点击“开始 AI 评图”后，可以得到：

- 是否满足任务书要求的基础功能。
- 功能分区和功能位置是否合理。
- 主要流线是否顺畅，是否存在明显交叉干扰。
- 平面是否具有设计性、趣味性和几何多样性。
- 图纸或说明中缺少哪些表达。
- 下一步应该先改什么。

### 3.2 面向教师

教师可以快速看到：

- 学生方案在功能逻辑上的主要问题。
- AI 建议依据了哪些 Wiki 知识条目。
- 哪些反馈是硬性问题，哪些只是优化建议。
- 分数和评价是否足够稳定，能否用于课堂讨论。

### 3.3 面向系统

系统需要拿到稳定结构：

- 分数。
- 等级。
- 总结。
- 问题列表。
- 修改建议。
- 引用依据。
- 可显示在图纸上的标注点。
- Agent 状态。

## 4. 第一版边界

### 4.1 第一版要做

- 只做“方案阶段”的功能与流线评价。
- 第一版可先评价学生提交的文字说明、任务书摘要和已上传图纸；如果接入多模态模型，则允许读取图纸中的空间、房间标注和大致流线关系。
- 优先使用 `wiki-test/wiki/评价维度/方案阶段/功能与流线` 下的 Wiki 内容。
- 输出固定 JSON。
- 有错误时返回清楚提示，不让前端崩溃。

### 4.2 第一版暂不做

- 不把模型识图结果当成精确 CAD 审图结果。
- 不直接承诺能精确判断走廊宽度、房间面积、柱网尺寸和所有文字标注。
- 不做复杂向量数据库。
- 不把 Agent 评价当成最终课程成绩。
- 不允许模型编造不存在的规范编号和案例来源。

### 5.1 来自项目和提交的信息

```json

    "building_type": "小型公共建筑",
    "owner_name": "张学生",
    "grade": "大三建筑学"
  },
  "submission": {
    "id": 12,
    "title": "方案阶段提交",
    "design_stage": "方案阶段",
    "description": "设计概念：以漂浮的花园为理念...",

```

### 5.2 来自 Wiki 的知识依据

第一版直接读取这些文件：

```text
wiki-test/wiki/评价维度/方案阶段/功能与流线/总览.md
wiki-test/wiki/评价维度/方案阶段/功能与流线/规范条文.md
wiki-test/wiki/评价维度/方案阶段/功能与流线/案例/经典案例/金泽21世纪美术馆.md
```

后端传给 Agent 的知识摘要：

```json
{
  "references": [
    {
      "title": "功能与流线 — 总览",
      "source_type": "评价维度",
      "excerpt": "评价建筑方案在功能满足、功能分区、流线组织和平面丰富性上的合理性。"
    },
    {
      "title": "功能与流线 — 相关设计规范",
      "source_type": "规范",
      "excerpt": "公共建筑中各类使用空间的平面和竖向交通组织，应方向明确、流线通畅。"
    }
  ]
}
```

### 5.3 输入不足时的处理

| 情况 | Agent 处理 |
| --- | --- |
| 没有上传任务书 | 正常评价，但不能判断“是否满足任务书全部功能”，并写入 `missing_information` |
| 没有上传平面图 | 不直接判断具体空间位置和流线节点，只评价说明文字中的功能逻辑 |
| 没有设计说明 | 返回“信息不足”，分数不能高于 60 |
| 没有 Wiki 依据 | 可以评价，但 `confidence` 降低，并标注“暂无知识库依据” |
| 只有效果图 | 不做流线细节判断，只提示需要补充平面图和总平面图 |

## 6. 大模型与多模态能力

### 6.1 调用哪个大模型

当前项目后端已经预留 OpenAI 调用入口，配置项在 `.env` 中：

```text
LLM_PROVIDER=openai
LLM_MODEL=gpt-4o-mini
OPENAI_API_KEY=
```

这里的 `gpt-4o-mini` 是当前工程默认占位值，不是最终模型选型。正式接入功能与流线 Agent 时，模型必须满足两点：

- 如果只分析任务书、设计说明和 Wiki 依据，可以使用文本 GPT 模型。
- 如果要分析平面图、总平面图和分析图，必须使用支持图像输入的多模态 GPT 模型。

因此功能与流线 Agent 可以调用 GPT 大模型。第一版建议分两级：

| 阶段 | 建议模型能力 | 用途 |
| --- | --- | --- |
| v1 文本+弱读图 | 支持文本和图像输入的 GPT 模型 | 读取设计说明、任务书摘要、Wiki 依据和图纸截图，生成结构化反馈 |
| v2 强读图 | 多模态 GPT + 图纸预处理/OCR/标注提取 | 先提取房间名称、入口、流线、功能泡泡，再交给 Agent 判断 |

如果只是评价设计说明和任务书摘要，文本模型即可。  
如果要让 Agent 看平面图、总平面图和分析图，就必须使用支持图像输入的多模态 GPT 模型。

根据 OpenAI 官方图像与视觉文档，OpenAI API 支持把图片作为输入，模型可以分析图片，也可以读取图片中的部分文字；图片可以通过 URL、Base64 data URL 或文件 ID 传入。文档同时说明，图像会计入 token，且模型在图像形状、原始尺寸、计数和细节读取方面存在限制。  
参考：<https://platform.openai.com/docs/guides/images-vision>、<https://platform.openai.com/docs/models>

### 6.2 是否具有多模态识别能力

可以具有，但要分清楚能力边界。

多模态 GPT 可以帮助识别：

- 图纸中较明显的房间名称、入口、主路径和功能分布。
- 平面布局的大致组织方式。
- 是否存在明显的空间割裂、流线绕行、功能堆叠。
- 总平面中建筑入口、外部广场、停车、服务区等明显关系。

但它不应被当作精确工具来使用：

- 不能保证准确读取所有小字标注。
- 不能稳定计算房间面积。
- 不能精确判断走廊宽度是否达到规范数值。
- 不能替代 CAD/BIM 或人工审图。
- 对低清晰度、压缩严重、手绘潦草或图文重叠的图纸会明显失准。

### 6.3 是否能准确阅读图纸内容

第一版结论：可以辅助阅读，但不能保证准确。

功能与流线 Agent 应把图纸识别分成三个置信层级：

| 置信层级 | 判断方式 | 输出策略 |
| --- | --- | --- |
| 高置信 | 图纸标注清楚，房间名、入口、主要路径可读 | 可以指出具体功能区和流线问题 |
| 中置信 | 能看出空间大致关系，但细节不清 | 用“可能”“建议核对”表达，不做硬性结论 |
| 低置信 | 图纸模糊、缺少平面图或标注不可读 | 不做图纸细节判断，只提示补充材料 |

因此第一版提示词必须要求模型区分“我看到了什么”和“我推测了什么”。  
如果模型不能确定，必须写入 `missing_information` 或 `uncertain_observations`，不能强行下结论。

## 7. 评价维度

功能与流线 Agent 第一版评价 4 个子项：

| 子项 | 分值 | 评价重点 |
| --- | ---: | --- |
| 功能满足 | 30 | 是否满足任务书要求，是否缺少基础功能或关键空间 |
| 功能分区 | 25 | 功能放置区域是否合理，是否有明显错位或互相干扰 |
| 流线分析 | 25 | 主要人流、服务流线、内部流线是否顺畅，是否有明显交叉 |
| 平面丰富性 | 20 | 是否只是机械满足功能，是否具有设计性、趣味性和几何多样性 |

总分为 100 分。

## 8. 评分标尺

### 8.1 功能满足

| 分数 | 判断 |
| ---: | --- |
| 0-12 | 明显缺少任务书要求的基础功能，或主要功能无法对应项目类型 |
| 13-20 | 基础功能大体出现，但有关键功能缺漏、面积/数量表达不足或功能关系不完整 |
| 21-26 | 主要功能基本满足，少量辅助功能或配套空间需要补充 |
| 27-30 | 功能构成完整，能回应任务书要求，并能看出主次关系 |

评价重点：

- 是否有任务书要求的核心空间。
- 是否缺少入口门厅、公共活动、管理、服务、后勤、卫生间、交通等基础功能。
- 是否把“概念空间”写得很充分，但基础使用功能不完整。
- 如果无法获得任务书，应降低置信度，不能断言“功能已完全满足”。

### 8.2 功能分区

| 分数 | 判断 |
| ---: | --- |
| 0-10 | 功能放置明显混乱，例如安静空间贴近高噪声空间、后勤穿越公共核心区 |
| 11-17 | 有基本分区，但公共/私密、动/静、服务/使用关系不够清楚 |
| 18-22 | 分区较清晰，少量功能位置需要调整 |
| 23-25 | 分区清楚，功能位置与使用逻辑、场地条件和人群行为一致 |

评价重点：

- 公共区、安静区、服务区、后勤区是否有清楚边界。
- 功能位置是否符合使用频率和开放程度。
- 是否存在明显错误，例如卫生间、设备、后勤、办公、公共大厅等关系不合常理。
- 总平面和一层平面是否能互相对应。

### 8.3 流线分析

| 分数 | 判断 |
| ---: | --- |
| 0-10 | 主入口、主要路径和服务流线不明确，存在严重交叉或绕行 |
| 11-17 | 主流线基本存在，但方向不够清楚，有局部交叉或干扰 |
| 18-22 | 流线基本顺畅，不同流线有一定分离，少量节点需要优化 |
| 23-25 | 主要人流、内部流线和服务流线层次清楚，路径自然，干扰少 |

评价重点：

- 人从入口进入后是否知道去哪里。
- 主要公共流线是否顺畅。
- 后勤、服务、内部管理流线是否干扰公众使用。
- 是否有死胡同、过度绕行、穿越重要空间等问题。

### 8.4 平面丰富性

| 分数 | 判断 |
| ---: | --- |
| 0-8 | 平面只是机械排布房间，几乎没有空间组织、变化或设计意图 |
| 9-13 | 能满足基础功能，但平面较平淡，空间体验和几何关系较弱 |
| 14-17 | 在满足功能基础上有一定空间层次、几何变化或公共空间设计 |
| 18-20 | 平面兼顾功能和设计性，空间有趣，几何关系丰富且不影响基本使用 |

评价重点：

- 是否只是“把房间放进去”，还是有空间组织。
- 公共空间是否有层次、节点和停留价值。
- 几何关系是否丰富但仍服务功能。
- 形体或平面趣味是否造成使用混乱。

## 10. 输出约束

Agent 输出必须满足：

- `score` 必须是 0 到 100 的数字。
- `sub_scores` 四项总分应接近 `score`，允许 2 分以内误差。
- 四项子分必须是“功能满足、功能分区、流线分析、平面丰富性”，不能改名。
- `must_fix` 最多 3 条。
- `should_improve` 最多 4 条。
- `strengths` 最多 3 条。
- 每条建议都必须能被学生执行，不能只写“加强设计逻辑”。
- 引用依据只能来自输入的 Wiki references，不允许编造新来源。
- 如果没有足够信息，必须写入 `missing_information`。
- 图纸识别不确定时，不允许用确定语气；必须写“可能”“需人工核对”或写入 `uncertain_observations`。
- 不允许使用“完美”“极差”等过度绝对化表达。
- 不允许替代教师下最终结论，只能给“辅助评价”。

## 11. 系统提示词

以下是第一版系统提示词草案。

```text
你是 ArchCritic 中的“功能与流线 Agent”，角色是建筑设计课助教。

你的任务是评价学生建筑方案在功能满足、功能分区、流线分析和平面丰富性方面的问题。

你必须遵守以下原则：
1. 你只评价“功能与流线”相关问题，不评价结构体系、立面造型或图面排版。
2. 你必须使用建筑设计教学语言，反馈要像老师评图时给学生指出修改方向。
3. 你不能编造不存在的规范、案例、条文或图纸内容。
4. 如果输入信息不足，你要明确说明缺少什么，而不是假装已经看到了。
5. 你不能把 AI 评价说成最终成绩，只能说是辅助评图建议。
6. 你必须输出合法 JSON，不能输出 Markdown，不能输出解释性前言。
7. 所有建议必须具体、可执行，学生看完后知道下一步改哪里。
8. 如果你读取图纸内容不确定，必须说明“不确定”或“需人工核对”，不能把推测写成事实。
9. 平面丰富性只评价平面空间组织是否有设计性、趣味性和几何多样性，不评价表皮风格。
```

## 12. 用户提示词模板

后端每次调用 Agent 时，把变量填入下面模板。

```text
请根据以下项目资料，完成“功能与流线”评价。

【项目信息】
- 项目名称：{project.name}
- 建筑类型：{project.building_type}
- 提交人：{project.owner_name}
- 年级：{project.grade}
```

## 13. Wiki 依据注入方式

第一版不用向量数据库，先做规则读取：

1. 根据 `design_stage` 判断阶段。
2. 如果是“方案阶段”，读取：
   - `功能与流线/总览.md`
   - `功能与流线/规范条文.md`
   - `功能与流线/案例/经典案例/*.md`
3. 提取：
   - 一级标题。
   - 维度说明。
   - 评图应用。
   - 可引用观点。
4. 拼成不超过 1200 字的知识摘要传给 Agent。

这样做的原因是当前 Wiki 数据量很小，规则读取比向量库更稳定，也更容易检查。

## 16. 失败兜底

| 问题 | 处理方式 |
| --- | --- |
| 模型没有返回 JSON | 后端重试 1 次，仍失败则返回“功能 Agent 输出格式错误” |
| 分数超过 100 | 后端截断到 100，并记录日志 |
| 引用了不存在的 Wiki 标题 | 删除该引用，并降低置信度 |
| 没有平面图 | 正常返回，但写入 `missing_information` |
| 图纸识别不确定 | 正常返回，但写入 `uncertain_observations`，并降低置信度 |
| OpenAI 接口失败 | 前端显示“功能 Agent 暂时不可用”，不影响项目和图纸保存 |

## 17. 测试样本

第一版至少准备 3 个测试样本：

| 样本 | 目的 |
| --- | --- |
| 只有设计说明，无图纸 | 测试信息不足兜底 |
| 有总平面图和一层平面图 | 测试正常评价流程 |
| 设计说明很短 | 测试低置信度和补充信息提示 |
| 平面只有简单矩形房间排列 | 测试平面丰富性评价 |
| 图纸模糊但文字说明完整 | 测试多模态不确定性表达 |

## 18. 验收标准

功能 Agent v1 完成后，应满足：

- 点击“开始 AI 评图”后，功能与流线分项来自真实 Agent。
- Agent 输出合法 JSON。
- 右侧报告可以正常渲染。
- 至少引用 1 条 `wiki-test/wiki` 中的依据。
- 没有图纸时不报错。
- 没有 Wiki 文件时不报错。
- 后端测试通过。
- 连续运行同一个样本 3 次，输出结构稳定，分数波动不超过 8 分。
- 对缺少任务书或缺少平面图的样本，必须返回信息不足提示。
- 对图纸内容不清楚的样本，不能编造房间名称、面积或流线。

## 19. 第一版推荐结论

第一个真实 Agent 应先做“功能与流线 Agent”，因为它最适合当前产品阶段：

- 建筑教学中最容易被学生理解。
- Wiki 中已经有规范和案例数据。
- 可以先用文本和基础多模态能力起步，不强依赖复杂图像识别。
- 输出可以直接映射到右侧报告和历史记录。

第一版的核心不是让 AI “像老师一样全面评图”，而是让它稳定完成一个窄任务：  
判断方案是否满足基础功能、功能位置是否合理、流线是否清楚、平面是否具有设计性，并给出有依据、可执行、可保存的反馈。
