# ArchCritic Demo 后端开发与前端对接设计

编写日期：2026-05-12  
适用阶段：Demo 原型开发  
目标：把当前三栏前端界面逐步接入后端，形成“填写信息、上传图纸、开始评图、查看报告、追溯依据、查看历史”的完整演示流程。

## 1. Demo 的产品目标

当前 Demo 不追求完整正式系统，先做一个能向老师和成员清楚演示的研究型原型。

第一阶段要让用户完成一条主流程：

```text
填写项目信息
-> 选择设计阶段
-> 上传不同类型图纸
-> 点击开始 AI 评图
-> 查看图纸标注和右侧评图报告
-> 查看知识库依据、历史版本和 Agent 状态
```

这个流程跑通后，前端成员可以继续打磨界面，知识库成员可以继续补依据，你可以继续替换真实单 Agent、多 Agent 和知识库能力。

## 2. 用户使用体验

用户进入页面后，看到的是一个建筑设计评图工作台。

左侧负责提交材料：用户填写项目名称、建筑类型、提交人、年级，选择当前设计阶段，再上传总平面图、一层平面、分析图或效果图。  
中间负责看图：用户可以切换图纸类型，放大、缩小和拖动画面。  
右侧负责看结果：用户点击开始评图后，系统生成总分、分项评分、必须修改、建议优化、当前优势和知识库依据。  
底部负责看过程：用户可以看到历史版本、分数变化和多个 Agent 的评审状态。

| 左侧设计阶段 | 概念阶段、方案阶段、图纸阶段 | 保存提交阶段，按阶段选择评价框架 | 高 |
| 左侧图纸上传 | 总平面图、一层平面、分析图、效果图 | 文件上传、文件分类、文件访问地址 | 高 |
| 左侧设计说明 | 文字说明 | 保存提交说明 | 高 |

| 中间图纸区 | 图纸预览、缩放、切换 | 返回图纸地址、图纸类型、AI 标注点 | 高 |
| 右侧总分与分项 | 总分、等级、维度分 | 返回结构化评图报告 | 高 |

## 4. 后端最小模块设计

### 4.1 项目模块

用途：保存一个设计项目的基本信息。

需要保存：

| 字段 | 说明 |
| --- | --- |
| project_id | 项目编号 |
| name | 项目名称 |
| building_type | 建筑类型 |
| owner_name | 提交人 |
| grade | 年级 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

建议接口：

```text
POST /api/projects
GET /api/projects
GET /api/projects/{project_id}
PATCH /api/projects/{project_id}
```

前端对应：

- 左侧“项目信息”表单
- 顶部“项目 / 类型”显示
- 底部历史版本所属项目

### 4.2 提交模块

用途：保存一次设计方案提交。一个项目可以有多次提交，形成版本追踪。

需要保存：

| 字段 | 说明 |
| --- | --- |
| submission_id | 提交编号 |
| project_id | 所属项目 |
| title | 提交标题，例如“第 1 版方案” |
| design_stage | 设计阶段 |
| description | 设计说明 |
| created_at | 提交时间 |

建议接口：

```text
POST /api/submissions
GET /api/projects/{project_id}/submissions
GET /api/submissions/{submission_id}
```

前端对应：

- 左侧设计阶段
- 左侧设计说明
- 底部历史版本追踪

### 4.3 图纸文件模块

用途：保存用户上传的本地图纸，并按类型关联到某次提交。

需要保存：

| 字段 | 说明 |
| --- | --- |
| file_id | 文件编号 |
| submission_id | 所属提交 |
| drawing_type | 图纸类型：总平面图、一层平面、分析图、效果图 |
| original_name | 原始文件名 |
| file_url | 前端可访问地址 |
| mime_type | 文件类型 |
| created_at | 上传时间 |

建议接口：

```text
POST /api/submissions/{submission_id}/files
GET /api/submissions/{submission_id}/files
GET /api/files/{file_id}
```

前端对应：

- “图纸上传”按钮
- 上传弹窗里的图纸类型选择
- 中间图纸区的图纸预览
- 中间顶部图纸标签切换

第一版只支持图片即可，先不做 PDF。PDF 可以后续再转图片或只保存文件。

### 4.4 评图模块

用途：点击“开始 AI 评图”后，调用 AI 生成结构化报告，并保存结果。

第一阶段先做单 Agent，后面再升级多 Agent。

需要保存：

| 字段 | 说明 |
| --- | --- |
| report_id | 报告编号 |
| submission_id | 所属提交 |
| overall_score | 总分 |
| grade | 等级 |
| summary | 总评 |
| must_fix | 必须修改 |
| should_improve | 建议优化 |
| optional_improvements | 可选提升 |
| strengths | 当前优势 |
| created_at | 生成时间 |

建议接口：

```text
POST /api/submissions/{submission_id}/evaluate
GET /api/submissions/{submission_id}/report
```

前端对应：

- “开始 AI 评图”按钮
- 右侧总分圆环
- 右侧四个维度进度条
- 右侧建议卡片

### 4.5 Agent 评价模块

用途：保存每个 Agent 或每个评价维度的结果。

需要保存：

| 字段 | 说明 |
| --- | --- |
| agent_evaluation_id | Agent 评价编号 |
| submission_id | 所属提交 |
| agent_type | Agent 类型 |
| dimension | 评价维度 |
| score | 分项分数 |
| summary | 分项总结 |
| issues | 发现的问题 |
| suggestions | 修改建议 |
| status | 状态：等待中、分析中、已完成、失败 |

建议接口：

```text
GET /api/submissions/{submission_id}/agent-evaluations
```

前端对应：

- 右侧分项评分
- 底部“多 Agent 评审矩阵”
- 中间图纸 AI 标注点

### 4.6 知识库引用模块

用途：让 AI 的建议有依据，而不是只给主观评价。

需要保存：

| 字段 | 说明 |
| --- | --- |
| reference_id | 引用编号 |
| report_id | 所属报告 |
| title | 引用标题 |
| source_type | 来源类型：规范、案例、课程任务书、常见问题 |
| excerpt | 简短依据 |
| dimension | 对应评价维度 |

建议接口：

```text
GET /api/reports/{report_id}/references
```

前端对应：

- 右侧“知识库追溯”
- 建议卡片中的依据说明

第一版可以先从 Markdown 文件中读取，不急着做复杂向量数据库。

## 5. 按钮与接口一一对应

| 前端按钮或动作 | 用户看到什么 | 后端动作 | 接口 |
| --- | --- | --- | --- |
| 新建评图 | 清空当前表单，准备新项目 | 可先只做前端清空；后续创建草稿项目 | 暂不必接 |
| 选择设计阶段 | 阶段按钮高亮，顶部阶段后续更新 | 保存到提交记录 | `POST /api/submissions` |
| 点击上传图纸 | 打开上传弹窗 | 暂无后端动作 | 暂不必接 |
| 上传并查看 | 图片出现在中间图纸区 | 保存文件并返回访问地址 | `POST /api/submissions/{id}/files` |
| 切换图纸标签 | 中间图纸切换 | 读取对应类型图纸 | `GET /api/submissions/{id}/files` |
| 开始 AI 评图 | 按钮进入分析中，右侧更新报告 | 创建项目、创建提交、上传文件、调用评图 | 组合调用 |
| 必须修改/建议优化/当前优势 | 切换建议卡片 | 使用已返回报告数据 | 不需要新接口 |
| 查看典籍 | 展开或跳转依据详情 | 读取引用依据 | `GET /api/reports/{id}/references` |
| 查看对比 | 展示不同版本变化 | 读取提交历史和报告分数 | `GET /api/projects/{id}/submissions` |
| 导出报告 | 下载报告文件 | 生成报告文件 | `GET /api/reports/{id}/export` |
| 系统设置 | 进入设置弹窗 | 读取或保存模型配置 | 后期再做 |

## 6. “开始 AI 评图”的推荐调用流程

点击“开始 AI 评图”时，前端不要只调用一个接口。第一版可以按下面顺序执行：

```text
1. 创建或更新项目
2. 创建一次提交
3. 上传本次提交中的所有图纸
4. 调用评图接口
5. 读取报告结果
6. 更新右侧报告、底部历史版本和 Agent 状态
```

对应接口：

```text
POST /api/projects
POST /api/submissions
POST /api/submissions/{submission_id}/files
POST /api/submissions/{submission_id}/evaluate
GET  /api/submissions/{submission_id}/report
```

为了 Demo 稳定，也可以先做一个整合接口：

```text
POST /api/demo/evaluate
```

这个接口一次接收项目、提交、图纸和说明，直接返回报告。  
但正式开发时，仍建议拆成项目、提交、文件、评图几个模块，后续更容易维护。

## 9. 推荐开发顺序

### 第一步：把上传和提交持久化

目标：刷新页面后，项目和图纸不丢。

交付：

- 项目信息能保存到数据库。
- 设计说明和阶段能保存到数据库。
- 图纸能上传到后端文件夹。
- 中间图纸区能显示后端返回的图片地址。

### 第二步：把右侧报告改成后端返回

目标：右侧不再写死 82 分和固定建议。

交付：

- 点击“开始 AI 评图”后调用后端演示评图。
- 右侧总分、分项进度条、建议卡片由接口返回。
- 出错时页面有清楚提示。

### 第三步：接历史版本和知识库依据

目标：底部和知识库区域不再只是展示图。

交付：

- 底部历史版本来自真实提交记录。
- 知识库追溯来自报告引用。
- 点击依据可以看到简短来源说明。

### 第四步：升级到真实单 Agent

目标：评图内容不再只是演示数据。

交付：

- 单 Agent Prompt v1。
- 结构化 JSON 输出。
- 失败时保留可读错误。
- 同一份测试样本能稳定返回报告。

### 第五步：简化多 Agent

目标：体现项目的核心研究特点。

交付：

- 场地 Agent。
- 功能 Agent。
- 形式 Agent。
- 结构 Agent。
- 综合评审 Agent。
- 底部 Agent 状态真实更新。

## 10. Demo 验收标准

本阶段完成后，至少要能做到：

| 验收项 | 通过标准 |
| --- | --- |
| 项目信息 | 输入后能保存，并同步顶部显示 |
| 图纸上传 | 至少 3 类图片能上传和切换查看 |
| 评图触发 | 点击按钮后能生成报告 |
| 报告展示 | 右侧不是一整段聊天，而是结构化卡片 |
| 历史版本 | 能看到至少 2 次提交记录 |
| 知识库依据 | 至少显示 2 条可读依据 |
| 演示稳定性 | 使用固定样本能完整演示 1 次，不需要临时修页面 |

## 11. 给团队成员的分工说明

前端成员负责检查：

- 页面是否好读。
- 上传弹窗是否清楚。
- 报告区域是否能一眼看出重点。
- 加载、失败、空状态是否有提示。

知识库成员负责提供：

- 每个评价维度的依据。
- 常见问题和修改建议。
- 案例或规范来源。
- AI 输出是否符合建筑设计课语境的核对意见。

你负责完成：

- 后端接口。
- 文件保存。
- 评图流程。
- 报告结构。
- 前后端联调。
- Demo 演示样本。

## 12. 一句话结论

当前前端已经具备演示工作台的基本形态，后端下一步应优先补“项目保存、图纸上传、提交记录、报告查询”四个基础能力，再逐步接入真实单 Agent、多 Agent 和知识库引用。
