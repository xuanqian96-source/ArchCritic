# ArchCritic 知识库处理与模型调用路线

本文说明如何把成员整理的 Obsidian 知识库，逐步处理成 ArchCritic 评图系统可以调用的 Wiki 知识库和知识图谱。目标不是让大模型“自由发挥”，而是让它在评图时能引用规范、案例和常见问题依据，从而提高回答的准确性、可追溯性和可靠性。

## 一、当前状态

当前已有 `知识库测试版` 文件夹，可以直接用 Obsidian 打开。它已经具备以下基础：

- 有 `.obsidian` 配置，可以作为 Obsidian 仓库使用。
- 有 `00 首页.md`，可以作为知识库入口。
- 有 `01索引`，用于进入规范索引和案例索引。
- 有 `02设计规范笔记`，整理了博物馆、民用建筑、防火、无障碍、照明等规范。
- 有 `03优秀案例笔记`，整理了 7 个博物馆或展览建筑案例。
- 有 `00原始资料`，保存 PDF 和案例图片原件。

这说明它已经适合“人阅读、团队维护”。但要让评图系统稳定调用，还需要再做一层“机器可读”的整理。

## 二、核心目标

知识库最终应同时服务两类对象：

- 对团队成员：像普通 Obsidian 笔记一样，可以阅读、补充、修改和建立链接。
- 对评图系统：像一个可检索资料库一样，可以根据学生方案自动找出相关规范、案例和常见问题，并把依据交给大模型。

因此不要把知识库只做成资料堆，也不要一开始就做成复杂数据库。建议采用“三层结构”：

1. 原始资料层：PDF、图片、网页摘录、案例图纸，作为证据来源。
2. Wiki 笔记层：人工整理后的规范条目、案例卡片、常见问题和评价维度说明。
3. 检索调用层：后端把 Wiki 笔记整理成可搜索的小卡片，评图时按需取用。

## 三、知识库应处理成什么样

每条可以被系统调用的知识，都应整理成“知识卡片”。一张知识卡片不一定是一个单独文件，也可以是一篇 Markdown 里的一个小节，但它必须包含以下信息：

| 字段 | 作用 | 示例 |
| --- | --- | --- |
| 标题 | 让人和系统知道这条知识讲什么 | 博物馆入口应具有明确导向 |
| 来源类型 | 区分规范、案例、常见问题、教学经验 | 规范 |
| 来源位置 | 标明来自哪个 PDF、案例或老师经验 | 《博物馆建筑设计规范》第 X 条 |
| 建筑类型 | 说明适用范围 | 博物馆、展览建筑、公共建筑 |
| 设计阶段 | 说明在哪个阶段使用 | 概念阶段、方案阶段、图纸阶段 |
| 评价维度 | 说明用于评什么 | 功能与流线、场地与回应、形式与构图 |
| 适用问题 | 说明学生方案出现什么情况时调用 | 入口不清、展厅流线回头路多 |
| 可引用内容 | 供模型直接引用的一两句话 | 观众流线应清晰连续，避免与后勤流线混杂 |
| 修改建议 | 供模型形成反馈 | 建议明确主入口、票务、序厅和展厅之间的先后关系 |
| 可信度 | 说明依据强弱 | 规范强依据、案例参考、经验建议 |

这一步很关键。只有资料被拆成明确的小卡片，系统才能在评图时准确取用，而不是把整篇 PDF 或整篇案例都塞给大模型。

## 五、知识图谱是什么，现阶段怎么做

知识图谱可以理解为“带关系的知识库”。它不只是存放很多笔记，还要说明知识之间的关系。

例如：

```text
博物馆入口设计
  关联 → 功能与流线
  适用于 → 方案阶段
  来源于 → 博物馆建筑设计规范
  可参考 → Moesgaard Museum
  常见问题 → 主入口不清、参观流线混乱
```

在 Obsidian 中，知识图谱可以先用双向链接和标签实现，不需要一开始开发专门的图数据库。

建议每篇知识笔记开头都写一段基础信息：

```markdown
---
source_type: 规范
building_types: [博物馆, 公共建筑]
stages: [方案阶段]
dimensions: [功能与流线]
reliability: 强依据
---
```

然后正文里使用 Obsidian 链接：

```markdown
关联维度：[[05评价维度/方案阶段/功能与流线]]
关联案例：[[03优秀案例笔记/Moesgaard Museum 莫斯加德博物馆]]
常见问题：[[04常见问题/功能与流线]]
```

这样做的好处是：团队成员在 Obsidian 里能看到关系图，后端程序也能读取这些标签和链接，逐步形成真正的知识图谱。

## 六、评图系统应该怎么调用知识库

评图系统调用知识库不应是“把整个知识库发给模型”。正确流程应是：

1. 用户上传图纸和设计说明。
2. 系统判断项目类型、设计阶段和当前评图维度。
3. 系统从知识库里检索少量最相关的知识卡片。
4. 系统把这些知识卡片连同图纸、说明一起交给大模型。
5. 大模型生成评图意见，并必须说明引用了哪些知识依据。
6. 前端在“知识库追溯”区域显示引用来源。

对应到 ArchCritic 的流程可以理解为：

```text
学生方案
  ↓
提取信息：建筑类型、阶段、图纸类型、设计说明
  ↓
知识库检索：规范 + 案例 + 常见问题
  ↓
模型评图：结合图纸和知识依据生成反馈
  ↓
输出报告：问题、建议、分数、引用依据
  ↓
前端展示：评图报告 + 知识库追溯
```

## 七、后端技术路线

建议分四步走。

### 第一步：文件夹直读，先跑通

当前 ArchCritic 后端已经能从 `WIKI_DIR` 读取 Markdown 文件，并把知识依据显示到前端。第一步可以先做一个适配器，让后端能读取 `知识库测试版` 中的 Markdown。

这一阶段不需要数据库，也不需要复杂检索。重点是：

- 统一 Markdown 模板。
- 让每篇笔记有标题、来源、评价维度和可引用观点。
- 后端能按设计阶段和评价维度读取相关条目。

适合当前 5 月底原型。

### 第二步：建立知识索引

当笔记数量变多后，不能每次临时扫整个文件夹。可以生成一个 `knowledge_index.json` 或 SQLite 表。

索引里保存：

- 文件路径
- 标题
- 来源类型
- 建筑类型
- 设计阶段
- 评价维度
- 关键词
- 摘要
- 可引用内容
- 原始来源

这样后端可以先查索引，再读取少量相关笔记。

### 第三步：加入语义检索

当知识库超过几十篇后，只靠关键词会不够。可以给每张知识卡片生成一段向量，用来做“意思相近”的检索。

例如学生写“入口空间很弱”，系统不只搜“入口”，还能找到：

- 门厅组织
- 主入口识别
- 参观流线起点
- 公共大厅导向

这一阶段可以使用轻量方案，不必一开始上复杂平台：

- 小规模：SQLite + 本地向量文件。
- 中规模：Chroma、LanceDB 或类似轻量向量库。
- 后期部署：再考虑云端向量数据库。

### 第四步：升级为知识图谱

当知识库维护稳定后，再把笔记里的关系提取成图谱。

图谱节点可以包括：

- 规范条文
- 案例
- 评价维度
- 常见问题
- 建筑类型
- 修改策略

图谱关系可以包括：

- 属于某个评价维度
- 适用于某个建筑类型
- 支持某个修改建议
- 参考某个案例
- 来源于某条规范

这一阶段可以先用 JSON 或 SQLite 表表达关系，不必马上使用 Neo4j 等专门图数据库。只有当关系查询非常复杂时，再考虑图数据库。

## 八、维护工作怎么分配

建议把维护工作分成四类。

### 资料收集者

负责收集 PDF、案例图片、网页资料和老师课堂经验，只放入 `00原始资料`，不直接改核心知识卡片。

### 知识整理者

负责把原始资料整理成规范笔记、案例笔记和常见问题笔记。重点是把长资料变成可引用、可检索的小段。

### 专业审核者

负责检查建筑学判断是否可靠，尤其是规范条文、消防、无障碍、面积尺度等内容。规范类内容必须严谨，不能随意发挥。

### 系统维护者

负责检查链接、标签、索引和后端调用是否正常。每次知识库结构变化后，都要跑一次链接检查和检索测试。

## 九、每条知识的质量标准

一条能被评图系统调用的知识，至少要满足以下标准：

- 说清楚来源，不能只有结论。
- 说清楚适用场景，不能所有项目都套用。
- 说清楚对应维度，例如功能、流线、场地、形式、图面表达。
- 有一句可以被模型直接引用的短句。
- 有一条面向学生的修改建议。
- 如果来自规范，原文不能乱改。
- 如果来自案例，要说明它只是参考，不是强制标准。

## 十、模型回答如何保证可靠

大模型调用知识库后，仍然可能出现过度推断。因此系统应限制模型的回答方式：

- 必须区分“图纸中能确认的内容”和“无法确认的内容”。
- 必须引用知识库来源，不能凭空说“规范要求”。
- 规范依据要优先于案例经验。
- 案例只能作为启发，不能作为硬性扣分标准。
- 如果知识库没有相关依据，模型应说明“当前知识库未提供明确依据”。
- 对图纸中看不清的文字、尺寸和房间名，要降低置信度。

## 十一、建议的近期落地计划

### 第 1 周：整理结构

- 保留 `知识库测试版` 作为 Obsidian 仓库。
- 增加 `04常见问题`、`05评价维度`、`99维护记录`。
- 为现有规范和案例笔记补充统一的基础信息。
- 把 4 个只有原始图片、还没有案例笔记的案例补成案例卡片。

### 第 2 周：接入后端

- 增加一个知识库读取适配器，让后端可以读取 `知识库测试版`。
- 把 `WIKI_DIR` 指向新的知识库目录。
- 让前端“知识库追溯”显示真实规范和案例依据。
- 用 3 到 5 个学生方案测试检索结果是否相关。

### 第 3 周：建立索引

- 生成 `knowledge_index.json`。
- 按建筑类型、设计阶段、评价维度、关键词筛选知识。
- 让评图 Agent 每次只读取最相关的 5 到 10 条依据。

### 第 4 周：增强检索

- 增加语义检索。
- 建立常见问题与规范、案例之间的关系。
- 让评图报告显示“引用依据”和“依据类型”。

## 十二、当前最推荐的技术路线

当前最稳妥的路线是：

```text
Obsidian Markdown 知识库
  ↓
统一模板和标签
  ↓
生成轻量知识索引
  ↓
按阶段、维度、建筑类型检索
  ↓
必要时加入语义检索
  ↓
评图模型引用知识依据
  ↓
前端展示知识库追溯
```

也就是说，短期先做 Wiki，不急着上复杂知识图谱；中期把 Wiki 结构化成索引；长期再把规范、案例、问题和修改策略之间的关系升级成知识图谱。

## 十三、对 ArchCritic 的具体建议

对于 ArchCritic 当前阶段，建议先完成以下三件事：

1. 把 `知识库测试版` 作为正式知识库原型，不再继续维护旧的测试 Wiki。
2. 为每篇笔记补充统一标签，让系统知道它适用于哪个建筑类型、设计阶段和评价维度。
3. 后端新增“知识库检索层”，让功能与流线 Agent 不只是读取固定的 5 篇 Markdown，而是根据学生方案自动选择相关依据。

这样做可以让系统从“能生成评图意见”升级为“能基于明确资料生成评图意见”，更符合教学研究原型的定位。
