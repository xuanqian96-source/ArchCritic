# ArchCritic Qwen3.6-Plus 图纸预处理与评图流程设计

日期：2026-05-15  
适用阶段：第一个真实 Agent 原型升级  
主模型：阿里云百炼 `qwen3.6-plus`

## 一、为什么继续使用 Qwen3.6-Plus

`qwen3.6-plus` 作为当前原型的主评图模型，定位不是简单“看图识物”，而是承担综合判断任务：

- 理解建筑设计说明；
- 阅读图纸中的空间、文字和功能关系；
- 结合知识库依据做建筑学评价；
- 输出结构化评分、问题和修改建议。

之前临时切换视觉模型，只是为了排查接口超时，不代表正式方案改用旧模型。正式流程仍以 `qwen3.6-plus` 为主模型，但不能再把整张高密度建筑图纸一次性直接丢给模型评图。

## 二、核心问题判断

当前慢的主要原因不是 API Key、网络或模型文本能力问题，而是图片调用链路不合理。

2026-05-15 对同一张上传图纸做了对照测试：

| 调用方式 | 结果 | 判断 |
| --- | --- | --- |
| 纯文本调用 `qwen3.6-plus` | 约 7.8 秒返回 | 模型和 Key 正常 |
| OpenAI 兼容接口直接传 base64 图纸 | 90 秒超时 | 当前代码的主要问题 |
| 官方公网图片 URL | 约 10 秒返回 | URL 图像链路正常 |
| 同一官方图片改为 base64 | 约 53 秒返回 | base64 明显拖慢 |
| 百炼临时 OSS URL 调用本地图纸 | 模型识别约 13 秒返回 | 模型本身能识别该建筑图纸 |

因此，准确结论是：`qwen3.6-plus` 可以识别这张建筑图纸，真正导致卡顿的是当前后端把本地图片转成 base64 后直接塞进模型请求体。百炼试用界面更接近“先上传文件，再把 URL 交给模型”的链路。

建筑图纸确实比普通照片更复杂，但它不是本次超时的首要原因。本次首要问题是图片传输方式。

正式流程应改为：

> 先把本地图纸上传为百炼可访问的 URL，再让模型读取；随后再根据需要做图纸预处理和 Agent 评图。

## 三、总体流程

用户上传图纸后，系统按以下顺序处理：

1. 保存原图；
2. 上传图纸到百炼临时 OSS 或正式 OSS，获得模型可访问的 URL；
3. 生成模型专用图纸材料；
4. 调用 Qwen3.6-Plus 进行图纸读取；
5. 形成结构化图纸摘要；
6. 功能 Agent 结合图纸摘要、设计说明和知识库进行评图；
7. 输出评分、问题、建议和置信度；
8. 前端展示报告和分析过程。

## 四、模块分工

| 模块 | 主要职责 | 是否调用大模型 |
| --- | --- | --- |
| 前端上传模块 | 上传原图、显示原图、展示处理状态 | 否 |
| 后端文件中转模块 | 将本地图纸上传到百炼临时 OSS 或正式 OSS，返回模型可访问 URL | 否 |
| 后端图纸预处理模块 | 保存原图、生成缩略图、裁切局部图、控制图片大小 | 否 |
| 图纸读取模块 | 读取整体布局、房间文字、入口、功能区、流线线索 | 是 |
| 功能 Agent | 按功能满足、功能分区、流线分析、平面丰富性评分 | 是 |
| 报告生成模块 | 整理为前端可展示的分数、问题、建议和依据 | 可用模型，也可程序整理 |
| 知识库模块 | 提供任务书、规范、优秀案例和常见问题依据 | 否，后续可接检索 |

## 五、后端图纸预处理设计

第一优先级不是压低图片清晰度，而是停止 base64 直传。

正式方案建议：

- 本地开发阶段：使用百炼“上传本地文件获取临时 URL”接口，获得 48 小时有效的 `oss://` URL；
- 生产阶段：使用正式阿里云 OSS 或腾讯云 COS，生成模型可访问的临时签名 URL；
- 调用百炼模型时，传入 URL，而不是传入 base64；
- 如果使用百炼临时 `oss://` URL，请在请求头中增加 `X-DashScope-OssResourceResolve: enable`。

后端不应只生成一张低清缩略图，而应保留多种用途的图片版本。

| 图片版本 | 用途 | 建议尺寸 |
| --- | --- | --- |
| 原图 | 前端查看、历史存档、后续人工复查 | 保留上传原尺寸 |
| 整体缩略图 | 让模型判断总布局、建筑位置、空间关系 | 长边 1200-1600 像素 |
| 文字增强图 | 提高黑白对比，辅助识别房间名和图例 | 长边 1200-1600 像素 |
| 局部裁切图 | 读取入口、核心功能区、交通节点、图例 | 每张 512-1024 像素 |
| 极简预览图 | 快速判断图纸类型，避免无效调用 | 长边 384-512 像素 |

正式评图不能只依赖极简预览图。极简图只用于快速判断图纸类型或接口健康，不用于最终评分。

## 六、局部裁切策略

第一版不需要做复杂 CAD 解析，可以先用规则裁切：

- 中心区域：判断主要功能空间和平面组织；
- 上下左右四个区域：判断入口、场地边界和周边功能；
- 图纸底部区域：读取标题、比例、图例和房间编号；
- 高对比区域：优先裁切文字密集、黑线密集的位置；
- 用户当前选中的图纸类型：优先处理，例如一层平面优先裁切平面核心区域。

后续如果效果不够，再增加 OCR 或图像分割算法。

## 七、图纸读取输出

图纸读取模块不直接评分，而是先输出一份“图纸摘要”。建议结构如下：

```json
{
  "drawing_type": "一层平面",
  "readable_level": "medium",
  "detected_spaces": ["门厅", "多功能厅", "图书阅览", "办公室", "卫生间"],
  "entrance_observations": ["主入口位于图纸下方偏中部"],
  "zoning_observations": ["公共活动空间与管理空间大致分开"],
  "circulation_observations": ["主流线从入口进入后连接主要公共空间"],
  "unclear_items": ["部分小字标注不可读", "服务流线需要更多图纸确认"]
}
```

这一步的目标是把“图片”变成“可评价的信息”。

## 八、功能 Agent 评分逻辑

功能 Agent 不再直接面对一张复杂图片，而是读取以下材料：

- 项目信息；
- 任务书或任务书摘要；
- 设计说明；
- 图纸摘要；
- 关键局部图；
- 知识库依据；
- 缺失信息列表。

评分仍采用四项：

| 维度 | 分值 | 判断重点 |
| --- | --- | --- |
| 功能满足 | 30 | 是否满足任务书和基础功能要求，缺失功能必须指出 |
| 功能分区 | 25 | 功能放置区域是否合理，是否有明显错位或干扰 |
| 流线分析 | 25 | 人流、服务流线、内部交通是否清楚，是否明显交叉 |
| 平面丰富性 | 20 | 是否只是机械满足功能，是否有空间层次、趣味和几何多样性 |

## 九、速度目标

第一版可接受目标：

| 输入情况 | 预期时间 |
| --- | --- |
| 1 张清晰平面图 + 设计说明 | 45-90 秒 |
| 2-3 张常规图纸 | 60-150 秒 |
| 多张复杂大图 | 2-4 分钟 |
| 纯文本说明评图 | 10-20 秒 |

如果目标是稳定控制在 1-2 分钟内，第一版建议每次只让功能 Agent 深读 1-2 张关键图纸，其余图纸只做辅助摘要。

## 十、图纸大小建议

用户可以上传较大的原图，但模型不直接读取原图。

| 项目 | 建议限制 |
| --- | --- |
| 单张原图上传 | 10MB 以内 |
| 前端展示原图 | 使用原图或浏览器压缩预览 |
| 模型单张图片输入 | 控制在 0.5-2MB |
| 单次模型图片数量 | 3-6 张，含整体图和局部图 |
| PDF 图纸 | 后续单独做 PDF 转图和分页处理 |

## 十一、置信度设计

报告必须显示模型判断的可靠程度。

| 置信度 | 条件 |
| --- | --- |
| high | 平面图清晰，房间名称可读，入口和流线明确 |
| medium | 能看出主要空间关系，但部分标注不清 |
| low | 缺少平面图、图纸模糊、文字不可读或任务书缺失 |

低置信度时，Agent 可以评分，但必须明确说明“哪些内容无法确认”。

## 十二、前端展示方式

右侧对话区应展示可理解的处理过程：

1. 已保存原图；
2. 正在上传模型可读图纸 URL；
3. 正在生成模型图纸材料；
4. 正在读取整体布局；
5. 正在读取关键局部；
6. 正在形成功能与流线判断；
7. 正在生成评分报告。

AI 对话界面应接入流式输出：

- 后端使用 SSE 向前端推送模型生成片段；
- 前端实时追加到对话气泡中；
- 模型最终报告完成后，再切换或同步到报告视图；
- 如果开启 `enable_thinking=true`，可接收 `reasoning_content` 字段，但产品展示建议命名为“分析过程”或“推理摘要”，避免让用户误以为这是完全可靠的最终结论。

报告区应展示：

- 总分；
- 四项分数；
- 必须修改；
- 建议优化；
- 当前优势；
- 缺失信息；
- 置信度说明；
- 使用的知识库依据。

## 十三、第一阶段开发范围

第一阶段只实现必要闭环：

1. 后端保留原图；
2. 后端把图纸上传到百炼临时 OSS，获得 `oss://` URL；
3. Qwen3.6-Plus 通过 URL 读取图纸；
4. 后端生成整体图和固定局部裁切图；
5. Qwen3.6-Plus 先输出图纸摘要；
6. 功能 Agent 再输出评分报告；
7. 前端对话区显示流式输出和处理状态；
8. 超时后返回明确原因，不让界面一直卡住。

暂不做：

- CAD 原生解析；
- 完整 PDF 多页解析；
- 精确房间面积计算；
- 自动识别所有空间边界；
- 教师端配置。

## 十四、后续升级方向

第二阶段可以增加：

- OCR 文字识别；
- 图纸局部自动检测；
- PDF 转图；
- 多图纸综合对比；
- 任务书结构化解析；
- 不同建筑类型的专属功能清单；
- 多 Agent 并行评图。

## 十五、关键原则

正式评图不能为了速度牺牲真实性。

系统可以压缩、裁切和整理图纸，但不能把看不清的内容写成确定事实。对于建筑学评价来说，清楚地区分“已识别内容”“推测内容”和“缺失内容”，比强行给出看似完整的结论更重要。
